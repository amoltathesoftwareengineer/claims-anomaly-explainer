# claims-anomaly-explainer

Detects suspicious insurance claim patterns and explains each flag in plain language. Pairs anomaly detection with feature attribution so investigators see why a claim was flagged, not just a score.

> **Status:** early development. The data pipeline, detectors and explanation layer are being built in the open. See the [Roadmap](#roadmap).

---

## Why this exists

Insurers receive millions of claims, and only a small number can be reviewed by a person. Anomaly detection models help by ranking claims that look unusual. But most of them return only a score, such as "0.93". An investigator then has to guess:

- Why is this claim unusual?
- Is it the amount, the billing code, the provider, the timing, or a combination?
- Is it genuinely suspicious, or just rare but legitimate?

A flag without a reason is slow to review and hard to trust. `claims-anomaly-explainer` aims to provide:

- **Anomaly detection** on claims data using several methods under one interface.
- **A reason with every flag:** which features pushed the claim away from normal, shown in plain language.
- **Review-focused metrics:** how many true problems are found when investigators can only review a fixed number of claims.
- **Reproducible benchmarks** on open claims datasets.

---

## What it produces

For every flagged claim, the output is planned to look like this (illustrative example):

```
Claim 10482   anomaly score: high
Why it was flagged:
  - Billed amount is much higher than typical for this procedure code
  - Provider submitted many claims for the same patient in a short period
  - Diagnosis and procedure combination is rare
```

A flag means "worth a human look", not "fraud". The final decision always stays with the investigator.

## Data

Real claims data is private. This project plans to use open and synthetic sources:

- **CMS DE-SynPUF:** synthetic Medicare claims released by the US Centers for Medicare & Medicaid Services
- **CMS Medicare Provider Utilization and Payment Data:** public provider-level billing summaries
- **Synthetic claims generated by this project,** with injected anomalies of known type, so explanations can be checked against the true cause

Datasets are **not** redistributed in this repository. Scripts download them from the original sources, and each dataset keeps its own license and citation requirements.

## Planned approach

### Detection methods compared

- **Rules:** simple limits on amount, frequency and code combinations
- **Statistical:** z-score and robust outlier measures per procedure or provider group
- **Machine learning:** Isolation Forest, Local Outlier Factor, autoencoders

### Explanation methods

- **Feature attribution:** SHAP-style contributions showing which fields drove the score
- **Peer comparison:** "this claim vs typical claims for the same procedure and region"
- **Plain-language templates:** turn attributions into short sentences an investigator can read

### Metrics

- **Precision at k and recall at k:** quality of the top k flagged claims (k = number of claims a team can review)
- **Detection of injected anomaly types**
- **Explanation accuracy:** on synthetic data, does the explanation point to the true injected cause?
- **Stability:** does the same claim get a similar explanation if the model is retrained?

## How it works

```
claims data (amount, codes, provider, patient, dates)
                    |
                    v
          cleaning + feature engineering
                    |
                    v
   detector (rules / statistical / ML) --> anomaly score
                    |
                    v
   explainer (attribution + peer comparison)
                    |
                    v
   ranked review list with a plain-language reason per claim
```

## Quickstart (planned)

```bash
git clone https://github.com/amoltathesoftwareengineer/claims-anomaly-explainer.git
cd claims-anomaly-explainer
pip install -r requirements.txt

# download and prepare a dataset
python -m claims_explainer.datasets.download --name desynpuf

# score claims and print explanations for the top flags
python -m claims_explainer.run --detector isolation-forest --top 20

# reproduce the benchmark table
python -m benchmarks.run_all
```

## Limitations and responsible use

- An anomaly is **not proof of fraud.** Unusual claims can be legitimate (rare conditions, new treatments). Flags should only be used to prioritise human review, never to deny a claim automatically.
- Models can learn biased patterns from historical data and unfairly flag certain providers or groups. Fairness checks are part of the roadmap.
- Results on public or synthetic data may not match results on a real insurer's data.
- Explanations show what drove the model's score, which is not always the real-world cause.
- This project is for research and education. Never upload real claims or personal data to issues, pull requests or demos.
